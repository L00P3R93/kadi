Overview & Quick Start

What the Push API does and how to send your first notification

What is the Push API?

An HTTPS API that lets a trusted server, in practice the game server, ask Kadi to send a web push notification to one or more players (“it’s your turn”, “your tournament starts in 5 minutes”), or to announce something to every registered device (maintenance, new version).

Kadi owns delivery: it finds the players, skips anyone who has not turned notifications on, applies limits, queues the pushes and returns a summary. Players’ devices, subscriptions and push keys never leave Kadi.

The two APIs

APIEndpointAudienceKey
Player pushPOST /api/v1/push-notifications1 to 100 named playersPlayer key
Broadcast/api/v1/push-broadcastsEvery registered deviceBroadcast key (separate)
Each key only works on its own endpoints; the other one gets 401. A leaked “your turn” key can never notify everyone.

Common to every request

  • JSON in, JSON out. Every response, including errors and unknown routes under /api, is JSON even if you forget Accept.
  • No cookies, no session, no CSRF token. It is not meant to be called from a browser (no CORS headers).
  • Use HTTPS only, and never put the key in a URL or a log.
  • 202 Accepted means queued, not shown. See Delivery & Urgency.

Quick start

On the Kadi server, generate a key. It prints the key (give it to the game server) and a hash (put it in Kadi’s .env):

php artisan push-api:key

# .env
PUSH_API_KEY_HASHES=<the hash>

Reload config (php artisan config:clear) and restart the queue workers, then from the game server:

curl -X POST https://kadi.online/api/v1/push-notifications \
  -H "Authorization: Bearer <the key>" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: table-7-turn-12" \
  -d '{"recipients":[1042],"title":"Your turn","body":"It is your move at table 7.","url":"/dashboard","tag":"table-7"}'

Expected: 202 Accepted with a JSON summary.

Bearer key

Send the key as a bearer token on every request:

Authorization: Bearer kpk_...
  • The API is disabled until a key hash is configured. With none configured every request gets 503, so a missing setting can never leave it open.
  • Kadi stores only the SHA-256 hash of a key (PUSH_API_KEY_HASHES), never the key. Presenting the hash as the key is rejected.
  • Keys are compared in constant time. Bad keys are throttled per IP; a valid key is never blocked by other callers’ failures.
  • Optionally restrict callers to known IPs with PUSH_API_ALLOWED_IPS. Other addresses get 403 before the key is even checked.

Two separate keys

KeyGenerateKadi .env variableWorks on
Player keyphp artisan push-api:keyPUSH_API_KEY_HASHES/push-notifications
Broadcast keyphp artisan push-api:key --broadcastPUSH_API_BROADCAST_KEY_HASHES/push-broadcasts

Both variables accept a comma separated list of hashes, which is how key rotation works without downtime.

Rotating a key

  • Run push-api:key and note the new key and hash.
  • Put both hashes in .env (old,new) and reload config.
  • Give the game server the new key and let it switch.
  • When nothing uses the old key, remove its hash and reload. The old key now returns 401.
If a key leaked, skip the overlap: replace the hash immediately.

Required headers

HeaderRequiredNotes
AuthorizationRequiredBearer <key>. Basic is rejected.
Content-TypeRequiredapplication/json on requests with a body.
Idempotency-KeyRecommended (required for real broadcasts)8–64 characters: letters, digits, -, _.

Why it matters

Networks fail. If your request times out you cannot know whether Kadi received it, and re-sending would notify the player twice. An Idempotency-Key makes retries safe.

  • Same key, same request: Kadi returns the original response again (header Idempotent-Replay: true) and sends nothing new.
  • Same key, different request: 422, so a bug on your side cannot silently drop a message.
  • Same key, still processing: 409. Wait and retry with the same key.
  • The order of recipients does not matter when comparing requests.
  • Keys are remembered for 24 hours and scoped to your API key.
Idempotency-Key: table-7-turn-12
Use one key per logical event (table-7-turn-12) and reuse it for every retry of that event. Do not generate a fresh key per retry.

POST /api/v1/push-notifications Push a notification to 1–100 players ▶
Player keyIdempotent600/min per key

Description

Looks up each recipient, skips players without a registered device, applies the per-player hourly cap, queues a push for every device of every remaining player, and returns a summary. Delivery is asynchronous through Kadi’s queue.

About broadcasts

For announcements to everyone (maintenance windows, tournaments, a new version), not one player. A broadcast goes to every registered device: logged-in players, and players signed out by the idle timeout (their device stays registered).

It cannot reach anyone who never turned notifications on, or who signed out explicitly (signing out removes that device on purpose, so the next person on a shared device never receives your notifications). Responses say devices, never users, for that reason.

Announcements only: maintenance, tournaments, new versions. Not marketing. Uses the broadcast key; the player key gets 401 here.

Caps

Exceeding a cap returns 429 with Retry-After. A refused request is not remembered: once the cap clears you can retry with the same Idempotency-Key. 503 means PUSH_API_BROADCAST_KEY_HASHES is empty (broadcasts disabled).

Sending from the server: push:broadcast

Operators on the Kadi server can use the artisan command (there is no admin screen). It enforces the same content rules and daily cap.

php artisan push:broadcast --title="Maintenance tonight" --body="Kadi will be offline 1am-2am EAT." --dry-run
php artisan push:broadcast --title="Maintenance tonight" --body="..."     # asks to confirm
php artisan push:broadcast --status=<id>
php artisan push:broadcast --cancel=<id>

--force skips the caps (command only; the API has no such option) and --yes skips the confirmation.

How it is sent

A broadcast is split into jobs of 200 devices. Each job sends its devices concurrently, deletes devices the push service says are gone, and adds to the counters; the last job marks the broadcast done. Jobs are retried up to 3 times (10s, then 60s backoff), and a retried job replaces its own notification (same tag) rather than stacking a duplicate. A very large send can delay per-player pushes unless the operator has given broadcasts their own queue worker.

What “accepted” means

202 means Kadi accepted the request and queued the pushes. It does not mean the notification has been shown.

  • Delivery is asynchronous, normally within seconds, through Kadi’s queue.
  • A player’s device can be offline. The push service holds the message for up to ttl seconds, then drops it.
  • Players may have several devices; each gets the push.
  • There are no delivery receipts.
  • Kadi retries a failing push up to 3 times (10s, then 60s). Subscriptions the push service reports as expired are removed automatically.

Urgency

A push goes through Google’s, Apple’s or Mozilla’s push service, and urgency tells that service how eager to be.

urgencyWhat the phone does
highDelivered at once, even to a sleeping phone (Android Doze, an idle iPhone) with the app closed. Use for time-sensitive things: “it is your turn”, “tournament starts in 5 minutes”.
normal (default)Delivered when the phone is next awake. An idle phone can hold these back for minutes or longer, until it is used again.
low, very-lowDeferred further, for example until charging or on Wi-Fi. For “nice to know” content.
  • Use high only for what a player would want interrupting them. Overuse makes players switch notifications off, and push services may deprioritise abusive senders.
  • high changes when the message arrives, not whether it may be shown. The limits are unchanged.
  • Combine with a short ttl for things that go stale ("ttl": 120 for a turn alert).
  • Whether a device shows anything also depends on the player’s own settings (notifications allowed, battery optimisation, Do Not Disturb). Kadi cannot override those.
  • Kadi can refuse high server-side (PUSH_API_ALLOW_HIGH_URGENCY=false), in which case it is a 422.

Writing good notifications

  • Plain text only. No HTML or markdown; it would appear literally.
  • Keep it non-sensitive. No balances, personal data or secrets. Lock screens are visible to others.
  • Short ttl for time-sensitive messages. “It’s your turn” is useless an hour later; use 60–300.
  • Use tag to collapse repeats. A per-table tag such as table-7 makes the newest alert replace the previous one.
  • url is a path inside Kadi, for example /dashboard. Where a path does not exist yet, use /.
  • Do not spam.

Error format

All errors are JSON with a message. Validation errors also include errors per field.

{ "message": "Unauthenticated." }
StatusMeaningWhat to do

403Caller IP is not on the allow-list.Ask Kadi to add the server’s IP.
404 / 405Wrong path, unknown broadcast id, or wrong method.Check the endpoint and id.

PHP (plain cURL)

$payload = json_encode([
    'recipients' => [1042],
    'title' => 'Your turn',
    'body' => 'It is your move at table 7.',
    'tag' => 'table-7',
    'urgency' => 'high',
    'ttl' => 120,
]);

$ch = curl_init('https://kadi.online/api/v1/push-notifications');
curl_setopt_array($ch, [
    CURLOPT_POST => true,
    CURLOPT_POSTFIELDS => $payload,
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_TIMEOUT => 10,
    CURLOPT_HTTPHEADER => [
        'Authorization: Bearer '.getenv('KADI_PUSH_KEY'),
        'Content-Type: application/json',
        'Idempotency-Key: table-7-turn-12',   // same value on every retry of this event
    ],
]);

$response = curl_exec($ch);
$status = curl_getinfo($ch, CURLINFO_RESPONSE_CODE);
curl_close($ch);

// 202: accepted. 409/429/5xx or a network error: retry later with the SAME Idempotency-Key.
// 401/403/422: do not retry, fix the request or the key.

Integration checklist

  • Key generated with push-api:key; only the hash is in Kadi’s .env; the key lives in the game server’s secret store.
  • Config reloaded and queue workers restarted on Kadi.
  • A test call returns 202, and the notification appears on a device that turned notifications on.
  • Unknown ids and players without a device are handled (not treated as errors).
  • Every event has a stable Idempotency-Key, reused on retries.
  • 401/403/422 are not retried; 409/429/5xx and network errors are retried with backoff.
  • Titles and bodies are short, plain text and contain nothing sensitive.
  • ttl is short for time-sensitive events, and tag collapses repeated ones.
  • urgency: high is reserved for things that should interrupt a player.
  • The key rotation procedure has been rehearsed once.
  • Broadcasts: a separate key from push-api:key --broadcast, a dry_run checked first, an Idempotency-Key on every real send, and only announcements are broadcast.

Security notes

  • A stolen player key can only send plain-text pushes to players who opted in, capped at 30 an hour each, with a site-local link. Rotate at once.
  • A stolen broadcast key can announce plain text to every registered device, but only 6 an hour and 4 a day in total, never with an off-site link, and a broadcast can be cancelled while it sends. It cannot push to individual players.
  • url must be a site path; absolute and protocol-relative URLs are rejected.
  • Responses and Kadi’s logs never contain the key, its hash, message text or player identifiers.
